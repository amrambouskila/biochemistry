Overview — what this is & why

Biochemistry is an ambitious multi-scale biological simulation platform. The grand goal: introduce any substance into a virtual organism and watch — in real-time 3D — how it propagates through the body and affects biology at every level, from individual atoms to whole organs.

The project models reality across eight scales of organization: atomic, molecular, organelle, cellular, tissue, organ, whole body, and universal organism. Each scale is a self-contained simulation engine with a defined input, output, timestep, and spatial resolution, and the scales connect through explicit "scale-crossing" contracts so a cellular engine can consume the concentrations produced by an organelle engine without knowing how that engine works internally.

The defining use case (from README.md): a user selects "cigarette smoke" and watches carbon monoxide travel through virtual lungs, cross alveolar membranes, and bind hemoglobin while benzene is absorbed, transported to the liver, and metabolized by cytochrome P450 into reactive intermediates that form DNA adducts — all visualized seamlessly from the macro scale of organs down to the nano scale of individual molecular interactions.

Watch out — what actually exists today
This is the single most important thing to internalize before reading the rest. The README, docs/MASTER_PLAN.md, and CLAUDE.md describe an enormous 8-phase vision, but the repository is currently a Phase-0 scaffold only (version 0.2.0). The backend exposes exactly one route (GET /health) and one module of physical constants. The frontend renders a single placeholder heading. None of the simulation engines, the element database, the periodic table UI, the molecular dynamics code, or the renderers exist yet — those are all planned work described in the master plan. Everywhere this guide describes an engine or endpoint that is not yet built, it is flagged as planned.

What is built and production-grade is the foundation: a correctly wired FastAPI backend with a 100%-coverage test gate, a React 18 + TypeScript-strict + React-Three-Fiber frontend with Vitest at 100% thresholds, a clean Docker Compose topology (Postgres, Redis, backend, frontend) with healthchecks, a dev/prod compose split, full launcher scripts implementing the standard [r]/[k]/[q]/[v] loop, a five-stage GitHub Actions CI pipeline, a manual semver release workflow, and a complete agent-tooling layer (hooks, skills, slash commands) that enforces the architecture rules on every edit.

Key concept — multi-scale from day one
The central design constraint, repeated throughout CLAUDE.md: every decision is evaluated through "will this still work when we scale up to the next phase?" A molecule renderer that can't handle 10,000 atoms is useless by Phase 3; a cell model that needs 10 minutes per simulated second is useless by Phase 5. Performance and scalability are core requirements from the first line of code, not afterthoughts.

Architecture

The design splits cleanly into "backend computes, frontend renders." The backend must be fully usable headless (via API + scripts); the frontend must be able to render pre-computed data without a live backend. REST handles setup and queries; WebSocket streams binary simulation frames.

Key concept — the four-property engine contract
Architecture Principle #1 in CLAUDE.md: every simulation engine must declare its input (state from the scale below), output (state to the scale above / visualization data), timestep (simulated time per step), and spatial resolution (smallest resolvable feature). Engines at different scales never reach into each other — they talk only through these four properties. This is enforced by the engine-protocol and scale-interface agent skills.

The scale chain

The system's spine is the chain of scales, each with its own canonical unit system. Data converts units explicitly at every boundary (never mid-calculation):

Process boundaries & data flow

Browser REST→FastAPI setup→Engine init→WS frames→Worker decode→Zustand→R3F render

Three running processes in production (per docker-compose.yml): the FastAPI backend container, the nginx-served frontend container, and the two data containers (Postgres, Redis). In production the frontend is static files served by nginx, which reverse-proxies /api/ and /ws/ to the backend (see frontend/nginx.conf). In dev, Vite serves the frontend with hot reload and the backend runs with --reload.

Today's reality
The "Engine init", "WS frames", "Worker decode", and "R3F render" stages above are all planned. Right now the data flow is: browser loads a static React page that renders one heading; the only working backend interaction is a /health probe used by the Docker healthcheck. The architecture is faithfully scaffolded so these stages can be filled in phase by phase.

Core modules

There are only two real backend code modules and one frontend component today. The rest of this section documents each, plus the planned engine modules described in the master plan so you know exactly where future logic will land.

FastAPI app + health route backend/src/main.py

The entire backend HTTP surface. Constructs the FastAPI app with title/description/version metadata and registers a single async route. Because FastAPI auto-generates OpenAPI, this app already serves interactive docs at /docs and the raw schema at /openapi.json — useful even before any real routers exist.

The /health route is load-bearing for orchestration: the Docker HEALTHCHECK and compose depends_on: { backend: { condition: service_healthy } } both gate on a 200 from it, and backend/tests/test_health.py asserts the exact body.

Where new routers attach
When Phase 1 adds backend/src/api/elements.py, the pattern (per the master plan) is one APIRouter per resource, included into this app via app.include_router(...). The version= field here should be bumped to track pyproject.toml at that point.
backend/src/main.pyApp construction + health route.
backend/tests/test_health.pyAsync test of /health via the ASGI client fixture.
Universal physical constants backend/src/constants.py

The single sanctioned home for numeric literals that carry physical meaning. Every value is SI and follows the 2019 SI redefinition, so the five defining constants are exact; GAS_CONSTANT is derived as AVOGADRO × BOLTZMANN (exact because both inputs are exact). Each constant has a one-line docstring with its symbol and units.

Key concept — data-driven, not hard-coded
Element masses, electronegativities, force-field coefficients, enzyme kinetics, and physiological parameters must never appear here or in simulation code — they come from the database or data files. The data-driven-check skill flags any literal in simulation code and routes it to the right home (constants module, element DB, force-field file, or YAML/SBML). The master plan expands this module with Bohr radius, Hartree energy, vacuum permittivity, and the Rydberg constant when Phase 1 needs them.
backend/src/constants.pyThe constants.
backend/tests/test_constants.pyParametrized CODATA reference validation + gas-constant approx check.

A placeholder: a full-viewport flexbox centering an <h1>Biochemistry</h1> on a #111 dark background in monospace. It exists to prove the React + Vite + TypeScript pipeline boots and to give the smoke test something to assert. Planned — Atomic engine (Phase 1) backend/src/simulation/atomic/ (not built)

Per docs/MASTER_PLAN.md Stage 1.2, the atomic engine is four standalone modules:

  • quantum.py — compute the full set of (n, l, m_l, m_s) quantum numbers for every electron, using empirical configurations from the DB (so Cr is [Ar]3d⁵4s¹ and Cu is [Ar]3d¹⁰4s¹, not the Aufbau prediction).
  • orbitals.py — compute |ψ|² probability density on a 64³ voxel grid: radial wavefunction via scipy.special.assoc_laguerre, angular via scipy.special.sph_harm, fully vectorized, cached as .npy. Precompute all 30 orbitals up to n=4.
  • spectra.py — emission/absorption wavelengths via the Rydberg formula, validated against the hydrogen Balmer series (Hα=656.3 nm, Hβ=486.1 nm, Hγ=434.0 nm).
  • ionization.py — successive-ionization energetics from empirical IE data.
Not built
These modules and their backend/src/simulation/ parent directory do not exist yet. This entry documents the contract so you know what to create and where.
Planned — Force-field / MD engine (Phase 2) backend/src/simulation/molecular/ (not built)

The master plan calls this "the most critical code in the entire project." Stage 2.2 breaks it into: a UFF parameter loader, bonded forces (bond/angle/dihedral), non-bonded forces (Lennard-Jones + Coulomb with a cKDTree neighbor list), a velocity-Verlet integrator, a Berendsen thermostat, and an MDEngine runner. The engine must be parameter-agnostic (it takes positions, masses, and force-field parameters without caring whether they're atoms or coarse-grained beads) so the same code drives Phase 3 CG-MD.

The headline validation is energy conservation: total energy drift < 0.1% over 10,000 steps in the NVE ensemble, plus equilibrium bond lengths (H₂=0.74Å, O₂=1.21Å, N₂=1.10Å) and angles (water 104.5°, methane 109.5°).

Not built
Requires RDKit (not yet a dependency) for structure generation. See section 15 for the full phase roadmap.
Planned — Multi-scale coupler & higher engines (Phases 3–8) backend/src/simulation/coupler/, pbpk/, … (not built)

Phases 3–8 add organelle (coarse-grained MD + reaction-diffusion), cellular (compartmental + Gillespie/tau-leaping gene expression), tissue (agent-based modeling), organ (standalone ODE systems per organ), whole-body PBPK (~20 coupled ODEs), and a universal-organism layer driven by allometric scaling. They all communicate through the SimulationEngine / ScaleCoupler protocols planned for backend/src/simulation/interfaces.py.

Not built
Architectural intent only. The scale-interface skill guards these boundaries when they're implemented.

Data models & contracts

No domain data models exist in code yet — there are no Pydantic schemas or SQLAlchemy tables. The contracts below are specified in the master plan and become real files in Phase 1+. The one concrete contract today is the WebSocket message envelope shape defined in CLAUDE.md.

Key concept — contracts are sacred and mirrored
Pydantic models on the backend and TypeScript interfaces on the frontend must mirror each other exactly. The post-tool-use hook fires a reminder whenever a /types/, /stores/, or /models/ file is edited: "verify the TypeScript interface matches the Pydantic model." A contract change is a minor semver bump and must be approved before drifting.

WebSocket message envelope (specified, not yet coded)

From CLAUDE.md (FastAPI section) — the canonical frame format for streaming simulation state:

Position arrays travel as Float32Array inside the MessagePack payload, never as JSON arrays of numbers — a 10,000-atom molecule at 30 fps is ~3.6 MB/s as binary vs. ~10× that as JSON.

Planned Phase-1 element contract (Task 1.1.1)

The first real data contract. The Pydantic models will live at backend/src/models/atomic/element.py and the mirroring TS interface at frontend/src/types/Element.ts:

ElementBase
atomic_number, symbol, name, group, period, block, category.
ElementProperties
electronegativity (Pauling), atomic_mass, radii (empirical/calculated/van_der_waals/covalent), ionization_energies[], electron_affinity, oxidation_states, melting/boiling points, density, phase_at_stp, crystal_structure, electron_configuration (+abbreviated).
Isotope
mass_number, atomic_mass, natural_abundance, half_life, decay_mode.
ElementFull
ElementBase + ElementProperties + list[Isotope]. The shape the frontend store fetches.

Canonical Phase-1 units: Ångströms for radii, eV for energies, Kelvin for temperatures, g/cm³ for density.

Nothing here is implemented yet
There are zero Pydantic domain models and zero SQLAlchemy tables in the repo today. The only Pydantic-derived shape in flight is the FastAPI app metadata. This section is the spec you build against, not a description of current code.

How to run it

The launchers wrap Docker Compose with the standard [r]/[k]/[q]/[v] control loop and layer the dev overlay on top of the base file automatically.

Docker (recommended)

  1. From the project root, run run_biochemistry.sh (macOS/Linux) or run_biochemistry.bat (Windows).
  2. The script runs docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build -d, building backend + frontend images and starting Postgres + Redis.
  3. Open the Frontend at http://localhost:5175, the Backend at http://localhost:8222, and API docs at http://localhost:8222/docs.
  4. At the menu prompt: [r] rebuild & relaunch (loops forever), [k] stop keep images, [q] stop + remove project images, [v] full cleanup (images + volumes). Unrecognized input reprints the menu without tearing down the stack.
Why two compose files
The base docker-compose.yml is prod-clean: no bind-mounts, no --reload. The launcher adds docker-compose.dev.yml, which bind-mounts ./backend/src into the container and overrides the command to add uvicorn --reload for hot reload. For a prod-style run, use only the base file: docker compose -f docker-compose.yml up --build -d.

Backend without Docker

  1. cd backend, then uv sync --extra dev to install runtime + dev deps.
  2. uv run uvicorn src.main:app --reload --port 8000 to serve the API.
  3. uv run pytest to run tests (enforces the 100% coverage gate).
  4. uv run ruff check . and uv run ruff format --check . to lint/format.

Frontend without Docker

  1. cd frontend, then pnpm install.
  2. pnpm dev to start Vite on http://localhost:5175.
  3. pnpm test:coverage for Vitest with the 100% thresholds; pnpm lint for ESLint; pnpm build for a production build.
Windows launcher run-context gotcha
The .bat launcher uses set /p for its interactive menu. Per the user's recorded preference, running a .bat via PyCharm's right-click → Run is a non-TTY context where set /p hangs and output buffers — run launchers from a real terminal (or enable "Emulate terminal" in the run config) instead of fixing the script.

How to edit & extend it

This is the owner-focused section: where things go and the exact pattern to follow. Because the project is scaffold-stage, "extending it" mostly means executing the next master-plan task — so the guidance below maps the immediate work to concrete files.

Key concept — read the plan, then fill the empty package
The build order is authoritative. Before writing any module, find its task in docs/MASTER_PLAN.md (it gives the exact target file, dependencies, and validation criteria), confirm prerequisite tasks are done, and only then implement. The agent skills enforce this if you're working with Claude/Codex.

To add a new REST endpoint (the immediate Phase-1 work)

  1. Create backend/src/api/<resource>.py with an APIRouter (one router per resource — elements, atoms, molecules…).
  2. Define request/response shapes as Pydantic v2 models under backend/src/models/<domain>/ — one model per file, mirroring any TS interface.
  3. Register the router in backend/src/main.py via app.include_router(router, prefix="/api/v1").
  4. Add an integration test under backend/tests/ using the client fixture from backend/tests/conftest.py. Coverage must stay at 100% or pytest fails.

To add a simulation engine

  1. Create the module under backend/src/simulation/<scale>/. The engine-protocol skill requires you to write the four-property docstring (input / output / timestep / spatial resolution) before any logic.
  2. Use NumPy ndarrays with explicit dtypes (np.float64 for positions/forces, np.int32 for indices); document array shapes; no Python loops over particles; use scipy.spatial.cKDTree for neighbor searches.
  3. Reference backend/src/constants.py for any physical constant; load domain parameters from the DB or data files — never hard-code them.
  4. Add a mirroring test under backend/tests/simulation/<scale>/ with at least one np.testing.assert_allclose check against a known analytical/published value. No mocking of physics.
  5. There is a slash command for this: .codex/commands/new-engine.md scaffolds the engine + test + interface contract.

To add a Three.js / R3F renderer

  1. Read docs/frontend-protocol.md first. It is the merge-gating contract.
  2. Put the component under frontend/src/components/three/. Use useMemo for geometry/material, useRef for Three.js objects (never state/Zustand), and useFrame for per-frame updates.
  3. Every new THREE.* needs a matching .dispose() in a cleanup path. Use InstancedMesh past ~100 objects, LOD past 10k, Points past 100k.
  4. Custom shaders go in frontend/src/shaders/ as separate .vert/.frag files — never inline template literals.
  5. Simulation state goes in a Zustand store under frontend/src/stores/; UI-only state stays in React component state.

Testing

Both sides target 100% coverage, enforced in-tool so a passing test run implies a passing gate. There are three tests today; every new module is expected to ship with its mirror test.

Backend — pytest

Configured in backend/pyproject.toml: asyncio_mode = "auto", addopts = "--cov=src --cov-report=term-missing --cov-fail-under=100 --strict-markers -ra", branch coverage on. The async HTTP test pattern uses an in-process client (no live server, no network):

backend/tests/test_health.pyAsserts GET /health returns 200 and {"status":"ok"}.
backend/tests/test_constants.pyParametrized CODATA validation; gas-constant pytest.approx check.

Frontend — Vitest + RTL

Vitest config in frontend/vite.config.ts: jsdom environment, 100% thresholds on lines/functions/branches/statements, src/main.tsx excluded from coverage. The known Vitest pitfall — no auto-cleanup — is handled in setup:

frontend/src/App.test.tsxRenders App, asserts the "Biochemistry" heading is in the document.

Validation discipline (for future numerical code)

The validation-protocol skill governs simulation tests: use np.testing.assert_allclose with documented tolerances (never == for floats), validate at least one case against a published reference value, parametrize over multiple elements/molecules/conditions, and never mock physics or the database. The master plan's GATE checkpoints (e.g., GATE 2.2: H₂ bond length 0.74±0.02Å, energy drift <0.1% over 10k steps) are the concrete validation targets.

Domain glossary

Terms a newcomer needs to follow the master plan and the (future) simulation code.

Scale
One of the eight levels of biological organization the project models: atomic, molecular, organelle, cellular, tissue, organ, whole body, organism. Each has its own engine and unit system.
Scale-crossing contract
The typed handoff between adjacent scales (e.g., molecular → organelle passes coarse-grained beads + reaction rates). Units convert explicitly at the boundary.
Engine four-property contract
Every simulation engine declares its input, output, timestep, and spatial resolution. The unit of architectural reuse.
Progressive fidelity
Running each region at one of four detail levels — full, reduced, statistical summary, or frozen/cached — chosen by camera distance, so compute is spent where the user is looking.
Force field
The parameter set (bond/angle/dihedral constants, LJ ε/σ, partial charges) that defines molecular potential energy. UFF for all-atom (Phase 2), MARTINI for coarse-grained (Phase 3). Loaded from data files, never hard-coded.
Molecular dynamics (MD)
Time-stepping atoms under force-field forces using the velocity-Verlet integrator. Correctness is judged by energy conservation in the NVE ensemble.
NVE / NVT ensemble
NVE = constant number, volume, energy (used to validate energy conservation). NVT = constant temperature, held by a thermostat (Berendsen here).
Neighbor list
A precomputed list of atom pairs within a cutoff (built with scipy.spatial.cKDTree) that turns O(N²) non-bonded force computation into ~O(N).
Orbital voxel grid
A 64³ grid of |ψ|² probability-density values for a hydrogen-like orbital, cached as .npy, rendered as an isosurface or volume in the frontend.
CPK coloring
The standard element color convention (C=gray, O=red, N=blue, H=white, S=yellow…) used by the atom/molecule renderers.
PBPK
Physiologically-based pharmacokinetic model — the ~20-ODE whole-body system (Phase 7) tracking a substance through tissue compartments via blood flow and partition coefficients.
Allometric scaling
Predicting physiological parameters from body mass via power laws (heart rate ∝ M^−0.25, metabolic rate ∝ M^0.75). The Phase-8 shortcut to parameterizing arbitrary organisms.
InstancedMesh / LOD / Points
Three.js scaling primitives: instancing past ~100 identical objects, level-of-detail past 10k, point sprites past 100k. Mandated by the frontend protocol.
MessagePack
Binary serialization for simulation frames over WebSocket; decoded in a Web Worker so the main render thread never blocks.
